SECTION 01

บทสรุปผู้บริหาร

TIL ต้องการเปลี่ยนการประสานงานที่กระจายอยู่ในโทรศัพท์, LINE และใบงานกระดาษ ให้เป็นระบบกลางที่ทุกฝ่ายเห็นข้อมูลชุดเดียวกัน ลดงานตกหล่น ลดการกรอกข้อมูลซ้ำ และทำให้ผู้บริหารติดตามผลได้ทันเวลา

“เข้าไว ซ่อมจบ ไม่ทำงานซ้ำ ติดตามงานได้แบบ Real time”
1

งานไม่ตกหล่น

ทุกงานเข้าสู่ Ticket Pool กลาง มีผู้รับผิดชอบ Priority และ Deadline ชัดเจน

2

เห็นสถานะทันที

ทีมและผู้บริหารดูความคืบหน้า งานค้าง และจุดติดขัดได้จาก Dashboard

3

ลดงานซ่อมซ้ำ

ระบบแจ้งเตือนเมื่อเครื่องเดิมเกิดปัญหาในหมวดเดิมภายในช่วงเวลาที่กำหนด

4

ลดการพิมพ์ซ้ำ

ช่างบันทึกงานและรูปจากหน้างาน ส่วน AI ช่วยอ่านใบงานโดยมี Admin ตรวจสอบ

สิ่งที่ขอให้ยืนยัน: วิสัยทัศน์และลำดับความสำคัญทั้ง 4 ข้อนี้ตรงกับเป้าหมายขององค์กร
SECTION 02

เป้าหมายและผลลัพธ์ที่คาดหวัง

OPERATION

ทำงานเป็นระบบเดียวกัน

SV, ST, QC และ Installation ใช้ข้อมูลลูกค้า เครื่องจักร งาน และอะไหล่ร่วมกัน ลดการถามซ้ำและการส่งต่อด้วยความจำ

FIELD SERVICE

ช่างทำงานได้แม้สัญญาณไม่ดี

Mobile PWA รองรับ Offline-first ข้อมูลจะรอ Sync เมื่อกลับมาออนไลน์ และแสดงสถานะให้ช่างเห็นชัดเจน

CONTROL

ตรวจสอบย้อนหลังได้

ทุกการสร้าง แก้ไข เปลี่ยนสถานะ และเคลื่อนไหว Stock ระบุผู้ทำ วันที่ และเวลา ผ่าน Audit Trail

MANAGEMENT

ตัดสินใจจากข้อมูลจริง

Dashboard แสดงงานค้าง เวลาตอบสนอง เวลาซ่อม งานซ่อมซ้ำ ผลงานทีม และสุขภาพ Stock

ผลลัพธ์ทางธุรกิจเมื่อส่งมอบครบ

  • ลดความเสี่ยงที่งานลูกค้าหรืองานภายในแผนกจะถูกลืม
  • ลดเวลาประสานงานระหว่าง SV และ ST เมื่ออะไหล่ตาม SO เข้าครบ
  • มีประวัติเครื่องจักรและงานซ่อมที่ค้นหาและ Export ได้เป็นมาตรฐาน
  • ติดตาม KPI ได้โปร่งใสจากเวลาและสถานะที่ระบบบันทึกจริง
  • ลดภาระ Admin จากผู้พิมพ์ข้อมูลเป็นผู้ตรวจสอบความถูกต้อง

SECTION 05

แนวทางการออกแบบที่เสนอ

01 · MOBILE

QR-first

หน้าแรกของช่างคือ QR Scanner เมื่อสแกนเครื่อง จะเห็นข้อมูลเครื่อง งานที่เปิดอยู่ PM ที่ใกล้ถึง และหมายเหตุลูกค้า

02 · FIELD

Offline-first

ช่างกรอกข้อมูลและถ่ายรูปได้เมื่อไม่มีสัญญาณ ระบบแสดงรายการรอ Sync อย่างชัดเจน และส่งเมื่อออนไลน์

03 · LANGUAGE

Thai-first

ภาษาไทยเป็นหลัก เก็บ English Technical Term และ Proper Noun เมื่อจำเป็นเพื่อรักษาความหมาย

04 · EVIDENCE

Evidence required

งาน Service ต้องมีรูปใบงาน รูปอะไหล่เสีย และรูปอะไหล่ใหม่เมื่อมีการเปลี่ยน จึงจะส่งงานได้

05 · CONTROL

Role-based & Auditable

แต่ละ Role เห็นและแก้ไขเฉพาะข้อมูลที่รับผิดชอบ ทุกการเปลี่ยนแปลงมี Audit Trail

06 · AI

Human verification

AI ช่วยอ่านใบงาน แต่ไม่บันทึกข้อมูลเข้า Ticket อัตโนมัติ Admin ต้องตรวจและยืนยันก่อนเสมอ

ข้อมูลสำคัญที่จะแสดงให้เหมาะกับผู้ใช้

ผู้ใช้ข้อมูลที่ต้องเห็นเด่นแนวทาง
ช่างหน้างานงานของฉัน, Priority, Deadline, ข้อมูลเครื่อง, รูปและ Stockปุ่มใหญ่ ขั้นตอนสั้น ใช้งานผ่านมือถือ
Admin / LeadTicket Pool, งานรอตรวจ, งานค้าง, การมอบหมาย และการค้นหาตารางและ Filter สำหรับทำงานจำนวนมาก
ST / Storeยอดคงเหลือ, Min/Max, การรับเข้า-เบิกจ่าย และสถานะ SOเห็น On-hand, Reserved และ Available แยกชัดเจน
ผู้บริหารภาพรวม, แนวโน้ม, KPI, จุดติดขัด และงานซ่อมซ้ำสรุปแบบ Read-only และเจาะดูรายละเอียดผ่าน Back-Office

SECTION 08

เกณฑ์ความสำเร็จและข้อกำหนดสำคัญ

เกณฑ์ด้านการใช้งาน

  • Admin เปิดงานและช่างปิดวงจรงานผ่าน QR ได้
  • งาน Service ส่งไม่ได้หากหลักฐานไม่ครบตามกติกา
  • ข้อมูลหน้างานทำ Offline และ Sync ภายหลังได้โดยผู้ใช้เห็นสถานะ
  • ค้นหาได้จากชื่อลูกค้า, Serial number, Part number, เลขใบงาน, PO และ SO
  • ประวัติเครื่อง Export แบบหนึ่งงานต่อหนึ่ง Row
  • Dashboard แสดงข้อมูลช้ากว่าระบบหลักไม่เกินประมาณ 60 วินาที

เกณฑ์ด้านการควบคุม

  • ทุกการแก้ไขสำคัญมี Audit Trail และไม่สามารถแก้ย้อนหลัง
  • ข้อมูลส่วนบุคคลแสดงเฉพาะ Role ที่จำเป็น ตามแนวทาง PDPA
  • Executive ไม่มีสิทธิ์แก้ไขข้อมูล
  • รูปและไฟล์ใช้ Link อายุสั้น ลดความเสี่ยงจากการแชร์ต่อ
  • LINE หรือ Push ขัดข้อง ระบบยังมี In-app Notification เป็นช่องทางสำรอง
  • AI อ่านใบงานไม่สำเร็จ ยังสามารถกรอกเองได้เสมอ
การยอมรับงานในแต่ละ Phase: ตรวจจากผลลัพธ์ใช้งานจริง (Exit Criteria) ของ Phase นั้น ไม่ใช้จำนวนหน้าจอเป็นตัววัดความสำเร็จเพียงอย่างเดียว
SECTION 09

ประเด็นสำคัญที่ต้องยืนยันกับลูกค้า

ทีมสามารถเริ่มออกแบบตามสมมติฐานด้านล่างได้ แต่คำตอบจะต้องได้รับการยืนยันก่อนเริ่ม Phase ที่เกี่ยวข้อง เพื่อหลีกเลี่ยงการแก้ไขงานและผลกระทบต่อกำหนดส่งมอบ

เจ้าของเลข PO และ SO

ยืนยันว่า “งานซ่อมซ้ำ” คือเครื่องเดิม + หมวดปัญหาเดิม ภายใน 72 ชั่วโมง และเป้าหมายไม่เกิน 1 เครื่องต่อเดือน หรือจำเป็นต้องมี Fault Code ที่ละเอียดกว่า

สมมติฐานปัจจุบันมี HQ และ Phuket เท่านั้น ต้องยืนยันว่ารถช่างหรือสถานที่อื่นถือ Consignment Stock และนับเป็น Warehouse เพิ่มหรือไม่

Mobile Platform

เสนอให้ใช้ PWA เพื่อส่งมอบเร็ว รองรับ Offline และไม่ผ่าน App Store โดยจะทบทวนอีกครั้งหาก Camera หรือ QR Scanner บนอุปกรณ์จริงไม่เพียงพอ

ระยะเวลาเก็บข้อมูล

สมมติฐาน Audit Log 7 ปี และรูปหลักฐาน 5 ปี ต้องให้ฝ่ายกฎหมายหรือผู้บริหารยืนยันตามนโยบายองค์กรและ PDPA

KPI เวลา

เอกสารต้นทางใช้คำว่า MTTR แต่ความหมายเขียนว่าเวลาตอบสนอง จึงเสนอเก็บและแสดงทั้ง MTTA (เวลาตอบสนอง) และ MTTR (เวลาซ่อมเสร็จ) แล้วเลือกตัวหลักหลังยืนยัน

PM Template

ลูกค้ามีขั้นตอน PM ราย Machine Model อยู่แล้วหรือไม่? ระบบสร้างและจัดการ Template อยู่ในขอบเขต แต่ข้อมูลขั้นตอนจริงเป็นข้อมูลที่ลูกค้าต้องจัดเตรียมและอนุมัติ

ข้อมูลมูลค่าในประวัติเครื่อง

ต้องแสดงค่าแรงและราคาที่เป็นทางการหรือไม่? สมมติฐานปัจจุบันใช้ค่าอะไหล่และค่าแรงที่ Admin กรอก หากต้องอ้างอิงราคาทางบัญชีจะเชื่อมกับคำตอบเรื่อง ERP

Customer Portal

สมมติฐาน Version 1 ไม่มีหน้าจอให้ลูกค้าเปิดหรือติดตาม Ticket ด้วยตนเอง หากต้องการให้วางเป็นโครงการ Post-v1 แยกต่างหาก

SECTION 10 · FINAL

Project Roadmap และ Timeframe

เสนอส่งมอบเป็น 5 Phase รวม 28 สัปดาห์ โดยแต่ละ Phase ให้ผลลัพธ์ที่นำไปทดลองใช้ได้จริง วันเริ่มต้นปฏิทินจะกำหนดหลังอนุมัติขอบเขตและความพร้อมของข้อมูลลูกค้า

P1
สัปดาห์ที่ 1–6 · Foundation

สร้างรากฐานและวงจร Ticket

ผู้ใช้และสิทธิ์, ข้อมูลลูกค้า/เครื่อง, QR Code, Audit Trail และ Ticket ขั้นพื้นฐาน

ผลลัพธ์: Admin เปิดงาน ช่างทำงานผ่าน QR และปิดงานได้ พร้อมตรวจสอบย้อนหลัง

P2
สัปดาห์ที่ 7–12 · Field Execution

เปลี่ยนงานหน้างานเข้าสู่ระบบ

Work Log, รูปหลักฐาน, Offline Sync, ค้นหา, ประวัติเครื่อง, Export และตรวจจับ Repeat Repair

ผลลัพธ์: ใบงานกระดาษไม่ใช่ข้อมูลหลัก และประวัติเครื่อง Export ได้ตามรูปแบบที่ตกลง

P3
สัปดาห์ที่ 13–18 · Inventory & Coordination

เชื่อมงานอะไหล่กับงานบริการ

Spare Parts, Stock หลายคลัง, QR เบิกของ, Min/Max, Quote/PO/SO Reference และ Notification

ผลลัพธ์: ช่างเช็ก Stock หน้างานได้ และ ST ยืนยัน SO ครบแล้วส่งงานกลับ SV อัตโนมัติ

P4
สัปดาห์ที่ 19–24 · Quality & Prevention

เพิ่มการป้องกันและการบริหารด้วยข้อมูล

PM แบบบังคับลำดับ, QC Inbound, Hook-up Requisition, Dashboard, KPI, Calendar, Skill Matrix และ Part Lifespan

ผลลัพธ์: เห็นผลงานและงานซ่อมซ้ำใกล้เคียง Real time ลดการสรุปข้อมูลด้วยมือปลายเดือน

P5
สัปดาห์ที่ 25–28 · Automation

ลดงานกรอกซ้ำและทำ Report อัตโนมัติ

AI Photo-to-Text, หน้าตรวจสอบข้อมูล, Scheduled Report และ Performance Tuning

ผลลัพธ์: Admin เปลี่ยนจากพิมพ์ใบงานเป็นตรวจสอบข้อมูลที่ระบบช่วยอ่าน

เงื่อนไขของ Timeframe

  • ระยะเวลา 28 สัปดาห์เป็นแผน Baseline หลังยืนยัน Requirement และ Design Direction
  • ลูกค้าจัดเตรียม Master Data, รายชื่อผู้ใช้/Role, PM Template, ตัวอย่างใบงาน และผู้ทดสอบตามกำหนด
  • การเชื่อม ERP, การเพิ่ม Native App หรือการเพิ่ม Scope หลังอนุมัติ ต้องประเมิน Timeline ใหม่
  • แต่ละ Phase มี Review, User Acceptance Test และ Sign-off ก่อนเข้าสู่ Phase ถัดไป
